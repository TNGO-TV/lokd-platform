## Confirmed latent defect FE-SEC-01

**Medium impact if the legacy evidence route is enabled: non-owner Operations can read owner-class evidence. Currently blocked at the Worker perimeter.**

- Source: `app/api/evidence/route.ts:137` checks only generic Operations membership. Lines 144–154 load `access_class` but return metadata without checking it; lines 155–167 fetch and return the object's bytes. The upload path accepts `owner`, `finance`, `compliance` and `operations` classifications at line 100. There is no owner check on the read path.
- Reproduction: owner uploads a synthetic `accessClass: "owner"` document into a fully migrated in-memory SQLite database and an in-memory bucket. A separately configured **non-owner Operations** account requests its known UUID. Metadata returns HTTP 200 and `accessClass: "owner"`; download returns HTTP 200 and exact synthetic content. Authentication headers in this test emulate the Worker-authenticated principal; no claim of remotely spoofing these headers is made.
- Preconditions: route exposure, an authenticated Operations principal and knowledge of the artifact UUID. This is not an anonymous read or UUID-enumeration finding.
- Current protection: `worker/index.ts:68` applies `liveSurfaceResponse`; `app/lib/live-surface.ts:3–9` blocks `/api/evidence` outside demo. In demo the evidence route's `requirePrivateRuntime` rejects the operation. Thus the isolated handler reproduction does **not** establish an exploit against the deployed Worker. Preserve these guards.
- Before enabling this retained route, enforce a centralized per-artifact authorization policy for metadata, content and verification, including explicit owner-only handling. Do not assume a stored access classification enforces itself. Also decide and implement finance/compliance group membership rather than silently treating them as unrestricted Operations metadata.

Evidence: [reproduction source](evidence-access-repro.mjs), [execution log](evidence-access-repro.log). Two isolated cases passed: demo rejection baseline and the intentionally successful unauthorized-class read. The latter passes because it proves the defect; it is not a security regression success. Run from repository root with `node --experimental-loader=./tests/cloudflare-loader.mjs docs/launch/release-security-2026-09-15/evidence-access-repro.mjs`.

## Hardening suggestions, not confirmed exploits

1. Replace `script-src 'unsafe-inline'` with a tested nonce/hash policy compatible with the application's renderer and authentication widgets. The present policy does not block injected inline script if a future HTML injection occurs; no such injection was identified in this review. Do not remove the allowance without validating actual rendering and login.
2. Centralize baseline non-CSP response headers in the Worker if consistent coverage is desired for early authentication, lock, health and failure responses. Those paths can bypass router-configured headers; current early responses are JSON/plaintext/redirects, so absence alone is not a demonstrated XSS or clickjacking exploit.
3. Enforce streaming request limits before fully buffering bodies for any future exposed large-upload route. The legacy evidence handler checks `request.text()` length after buffering; it is currently perimeter-blocked, and there is no anonymous resource-exhaustion reproduction here.

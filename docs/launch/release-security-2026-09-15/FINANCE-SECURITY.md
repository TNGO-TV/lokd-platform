# Finance/backend security review — 15 September 2026

## Result

No confirmed critical/high/medium financial-integrity vulnerability emerged from this bounded independent review. One **low-severity availability hardening finding** was reproduced offline. This is a source/control review with selected existing regression evidence and one new targeted probe; it is not a claim of exhaustive penetration testing or provider acceptance.

Reviewed the accepted source plus the one-space 0071 migration fix (workspace HEAD advanced to `8013f32` during coordinated release). No product changes, provider calls, accounts, secrets, production mutations or load tests were used for this security review.

## Finding FIN-SEC-01 — low / P3: public webhook body readers have no application deadline

**Locations:** `app/lib/paystack-test.ts:15`–17; `app/lib/booking-collections.ts:97`–98; `app/lib/payment-execution.ts:119`–120. The employee/partner test receivers have the same reader pattern, but the public test dispatcher reads their request first.

**Trigger and effect:** where the selected mode's key and database are configured, an unauthenticated caller can supply any syntactically valid 128-character hexadecimal signature and start a body without finishing it. The handlers wait on `reader.read()` before cryptographic verification. They enforce a 262,144-byte maximum but no body-read deadline. This can retain request/stream resources until the caller closes or platform limits intervene. No signature bypass, financial write or demonstrated platform-wide denial of service is claimed.

**Reachability:** `worker/index.ts:64`–65 explicitly routes `/api/paystack/booking/webhook`, `/api/paystack/transfers/live/webhook`, and `/api/paystack/test/webhook` before Clerk authentication. Thus these are mounted public paths, unlike an internal helper reached only by synthetic headers. A missing runtime key or DB returns before reading, so exploitability of each mode depends on its actual configuration; this review did not inspect secret values.

**Reproduction:** run `node --experimental-loader=./tests/cloudflare-loader.mjs docs/launch/release-security-2026-09-15/finance-stream-probe.mjs`. A fictional key, inert DB stub and controlled in-memory stream leave the actual test receiver pending for the observation window, then yield 401 when the stream closes. No DB access occurs. The existing bounded finance reader returns 408 for an equivalent stalled stream using its configurable 20ms test deadline. Source inspection establishes the absence of a deadline; the short probe does not purport to measure an indefinite hang.

**Suggested hardening:** extract/reuse the existing byte-and-time-bounded reader from `app/lib/finance-workflow-request.ts:5`–13 for all raw HMAC bodies, retaining the exact raw bytes for signature verification, cancelling on failure and releasing the reader lock. Keep the existing per-route size limit and reject unavailable modes before reading. Add one stalled-stream regression and one valid raw-signature regression per shared dispatch boundary.

## Additional bounded hardening suggestions

- Legacy authenticated finance mutation routes (`app/api/payment-execution/route.ts:19`, `app/api/booking-refunds/route.ts:29`, `app/api/payment-recovery/route.ts:17`) call `request.text()` before their string-length check. Standardize on a byte/time-bounded reader. Operations authentication and MFA precede these reads, so this is an authenticated resource-control gap, not an unauthenticated payment exploit.
- Provider fetch helpers use fixed Paystack hosts, disabled redirects and 20-second deadlines. Their `response.json()` parsing has no separate byte cap. A conservative response cap would contain a faulty upstream response; no attacker-controlled destination or demonstrated SSRF was found.
- Keep the hosted SQL splitter regression in release gates. Its reproduced 0071 whitespace failure was one release compatibility defect; the hosted retry still failed afterward. Central subsequently parenthesized 36 CASE expressions to match prior deployed migration style. All 165 new statements pass local splitting/schema checks and 44 targeted regressions pass; actual hosted outcome is recorded separately in the release receipt. This review found no need to loosen financial triggers.

## Limitations

No live provider behavior, bank accounting, deployment configuration secrets, brute-force/rate-limiting effectiveness or physical/network load behavior was tested. Root owns dependency/configuration/secret review and release validation; sibling reviews own other product/security areas. The conclusions above are confined to the named finance boundaries and retained regression scope.
